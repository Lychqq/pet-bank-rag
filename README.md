# Банковский RAG-ассистент

Производственный RAG-пайплайн для банковской клиентской поддержки.
Демонстрационный проект под позицию **AI Engineer (LLM/RAG)**.

## Архитектура

```
┌─────────────────────────────────────────────────────────┐
│                    Клиентский запрос                     │
└───────────────────────────┬─────────────────────────────┘
                            │
                            ▼
┌─────────────────────────────────────────────────────────┐
│              Гибридный поиск (Vector + BM25)             │
│                                                          │
│  pgvector (HNSW)  +  tsvector  →  RRF объединение       │
│  семантический поиск  точные совпадения  финальный рейтинг│
└───────────────────────────┬─────────────────────────────┘
                            │
                            ▼
┌─────────────────────────────────────────────────────────┐
│               Corrective RAG (Grader)                    │
│                                                          │
│  LLM оценивает релевантность найденных документов        │
│  Если нерелевантно → переписать запрос → искать снова    │
└───────────────────────────┬─────────────────────────────┘
                            │
                            ▼
┌─────────────────────────────────────────────────────────┐
│          Generation (Gemini 2.5 Flash)                   │
│                                                          │
│  System prompt с guardrails (не выдумывать ставки,       │
│  не показывать карточные данные, честное "не знаю")      │
└─────────────────────────────────────────────────────────┘
```

## Стек

| Компонент | Технология | Зачем |
|---|---|---|
| LLM (Пайплайн) | Gemini 2.5 Flash | Генерация ответов бота, Corrective RAG грейдер, OCR |
| LLM (Оценка) | Mistral 7B (через Ollama) | Судья для оценки качества через Ragas (в Colab) |
| Embeddings | SentenceTransformers (PyTorch) | Локальное векторное представление текста |
| Vector DB | PostgreSQL + pgvector (HNSW) | Семантический поиск |
| Full-text search | PostgreSQL tsvector | Точный поиск по ключевым словам |
| Hybrid search | RRF (Reciprocal Rank Fusion) | Объединение обоих типов поиска |
| Memory | PostgresChatMessageHistory | Персистентная история диалога |
| Evaluation | Ragas | Оценка качества retrieval и generation |
| Infrastructure | Supabase Cloud | Облачная PostgreSQL с поддержкой pgvector |

## Ключевые архитектурные решения

### Почему pgvector вместо Chroma
В банковском контексте Postgres — стандарт. pgvector добавляет векторный поиск в
существующую инфраструктуру, без отдельной специализированной БД. HNSW-индекс
обеспечивает логарифмическую сложность поиска вместо линейной.

### Быстрая пакетная индексация на GPU (Colab)
Так как мой ноутбук обладает слабой вычислительной мощностью, первичная загрузка (Data Ingestion) 200 объемных PDF-файлов производилась в **Google Colab**. Для максимального ускорения я отказался от абстракций LangChain в пользу "чистого" PyTorch (`SentenceTransformer(..., device="cuda")`). Это позволило вычислять эмбеддинги батчами по 256 текстов напрямую на видеокарте T4, сократив время индексации с нескольких часов до минут. Эта сверхбыстрая логика индексации теперь интегрирована напрямую в ядро проекта (`src/rag/pipeline.py`).

### Почему гибридный поиск (Vector + BM25)
Embeddings находят семантически похожее ("ипотека" ≈ "кредит на жильё"), но плохо
справляются с точными числами и кодами. tsvector/BM25 находит точные совпадения.
Для банковских запросов часто нужно и то и другое: клиент спрашивает про конкретный
продукт с конкретными цифрами.

### Почему Corrective RAG
Если retrieval нашёл "что-то похожее, но не то" — модель сгенерирует уверенный
неправильный ответ (галлюцинация). В банке это юридический риск. Corrective RAG
добавляет слой самопроверки: LLM-грейдер оценивает, действительно ли найденные
документы отвечают на вопрос. Если нет — запрос переписывается.

### Почему Postgres для истории диалога (не InMemory)
InMemoryChatMessageHistory исчезает при перезапуске сервера. При деплое новой версии
бот "забывал" контекст всех активных диалогов. Postgres — та же база Supabase, что уже
используется для pgvector, без новой инфраструктуры.

### Что можно добавить в production
- **pg_textsearch** — настоящий BM25 вместо tsvector, точнее ранжирует частичные
  совпадения. tsvector достаточен для демо, pg_textsearch — следующий шаг
- **LangGraph + checkpointing** — Corrective RAG реализован как простой Python-цикл,
  LangGraph добавил бы time-travel debugging, персистентность состояния агента
- **LangSmith observability** — сейчас логи пишутся в rag_logs таблицу, LangSmith
  даёт визуальный trace каждого шага с UI и алертами

# 3. Подключить базу данных

## Оценка качества (Evaluation) через Ragas

Основной боевой код в репозитории (`src/rag/pipeline.py`) использует **Gemini 2.5 Flash** для обеспечения максимального качества генерации ответов. 

Однако процесс оценки Ragas требует большого количества параллельных запросов к LLM (в роли "Судьи"). Из-за недостатка вычислительных мощностей (у меня слабый ноутбук), процесс тестирования и оценки я проводил в облачной среде **Google Colab**. 

### Технические вызовы при оценке:
1. **API Лимиты Gemini:** Первоначально я планировал использовать API Gemini и для ответов, и для оценки, но жесткие лимиты запросов (Rate Limits) бесплатного ключа не позволили прогнать тесты на всем датасете.
2. **Переход на локальный Mistral 7B в Colab:** В качестве обходного пути я развернул сервер Ollama с моделью Mistral 7B прямо внутри среды Colab, чтобы модель-судья работала локально и бесплатно.
3. **Проблемы с JSON-парсингом:** При увеличении объема выдачи поиска (k=15) для улучшения контекста, небольшая модель Mistral 7B перестала справляться со строгими промптами Ragas. Вместо требуемых сложных JSON-схем модель начала выдавать обрывки текста, что привело к ошибкам `RagasOutputParserException`. Библиотека Ragas автоматически ставит `0` баллов за нераспознанный ответ, что искусственно занизило итоговые оценки.

### Полученные метрики (Базовый пайплайн без коррекции):
* `context_precision`: **0.7661** (Высокая точность алгоритма гибридного поиска)
* `context_recall`: **0.0667** (Сложности с нахождением всех разрозненных кусков с первого раза)
* `answer_relevancy`: **0.6509** (Хорошая релевантность ответов бота)
* `faithfulness`: **0.4000** (Искусственно занижено из-за ошибок парсинга JSON у судьи)

### Влияние Corrective RAG (CRAG) на метрики:
При включении алгоритма самопроверки и переписывания запросов (CRAG), метрики поиска существенно выросли, так как бот научился исправлять собственные ошибки поиска:

* `context_precision`: **0.8114** (Выросла! CRAG отлично отфильтровывает мусорные документы)
* `context_recall`: **0.2500** (Выросла почти в 4 раза! Переписывание запросов спасает ситуации, когда первый поиск ничего не нашел)
* `answer_relevancy`: **0.5300** (Искусственно занижено из-за багов парсинга модели-судьи)
* `faithfulness`: **0.1667** (Искусственно занижено из-за багов парсинга модели-судьи)

**Итог:** 
Внедрение Corrective RAG доказало свою архитектурную эффективность: метрики качества поиска (`Precision` и `Recall`) значительно выросли. Просадка метрик генерации (`Faithfulness` и `Relevancy`) — это классический артефакт использования слабой локальной модели Mistral-7B в роли судьи (LLM-as-a-Judge). Модель-судья не справлялась с форматом строгих JSON-схем при оценке усложнившихся ответов, выдавая `RagasOutputParserException` (что автоматически приравнивается библиотекой к 0 баллов). Метрики retrieval (Precision и Recall) демонстрируют корректную работу поисковой системы. Метрики generation требуют повторной оценки с более сильной моделью-судьёй (например Gemini Pro или GPT-4) для получения достоверных результатов.
